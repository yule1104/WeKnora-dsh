盘古星火：AI 平台融合路线评估

比较“以 WeKnora 为底座”与“以星火为底座”，支持周期、投入与长期维护决策。｜2026-10-09

建议：长期统一 AI 平台优先采用 WeKnora 底座

复用知识库、Agent 与会话能力，星火继续承担项目、需求、本体和部署业务。若近期目标仅是在现有星火中增加知识检索，星火底座更适合快速交付。

路线 A · 推荐用于统一平台

WeKnora 底座 + 星火领域服务

用户、租户、知识库、Agent、会话由 WeKnora 统一；星火页面迁入 Vue，FastAPI 和业务数据库继续复用。

路线 B · 适合业务平台优先

星火底座 + WeKnora 知识服务

保留 React 项目工作台、现有 Agent 与会话；通过 API/MCP 使用 WeKnora 文档解析、检索和 RAG。

核心维度比较

维度路线 A：WeKnora 底座路线 B：星火底座
能力复用知识、Agent、会话能力复用充分；星火后端继续使用。星火业务页面复用充分；知识能力通过服务接口接入。
前期难度中高：React → Vue 页面重写；项目与租户权限映射。低至中：少量检索 API 接入快；完整知识管理体验工作量上升。
Agent / 会话原生对话、引用、工具展示可复用；需求/本体 Agent 通过模板与 MCP 接入。保留星火现有 Executor/会话；所需引用、附件、恢复等能力需逐项评估补齐。
租户与权限以 WeKnora 身份为主，星火业务权限仍需二次校验。以星火身份为主，需要映射 WeKnora 租户、知识库与文档访问范围。
业务连续性页面切换需培训与灰度；原星火后端和数据保留。现有界面与流程变化较小，早期切换风险较低。
升级维护定制 Vue 页面需合并上游；Gateway MCP 可减少 Go 核心修改。星火自主升级；WeKnora 独立升级后需验证 API/MCP 契约。
后续演进中等：引入更多知识、MCP、Skill 和 Agent 能力较自然。取决于范围：只做知识检索较可控；追求完整 AI 平台时补建成本高。
运维与成本两套后端持续运维；前期页面迁移投入较高，平台能力重复建设较少。同样保留两套后端；前期投入较低，长期成本取决于补齐能力和接口依赖面。

周期估算：按交付范围比较

交付目标路线 A路线 B
可演示版本5–7 周：只读项目工作台 + 知识/Agent 演示4–6 周：现有星火 + 知识检索/问答
统一平台 MVP9–12 周：项目、需求、本体候选与统一会话核心闭环12–16 周：保留星火入口，补齐知识管理、引用和权限等核心能力
生产可用版本14–18 周：回归、权限、审计、灰度与运维18–24 周：以达到上述相近平台能力为前提

以上为前期规划区间，并非承诺排期：假设 2 名前端、2 名后端、1 名 AI 工程师，测试/运维参与；工作可部分并行。需先完成代码与 API 盘点再确认。路线 B 若只做检索与问答，无需按完整平台周期投入；DSH Gateway 相关工作为两条路线共有成本。

选择依据与落地建议

选择 A：建设长期统一 AI 平台

适用于统一 Agent/会话、多租户知识服务，以及持续引入知识图谱、MCP、Skill 的目标。接受星火页面迁移投入。

选择 B：优先保留现有业务体验

适用于近期围绕项目、本体和需求交付，知识功能以 API 服务为主。先限定范围，避免后续不断追加平台能力。

推荐职责分工：WeKnora 负责产品入口与 AI 通用能力；星火负责业务事实与规则；DSH Gateway 负责复杂任务执行。

先落地：升级演练 → 项目绑定与只读工作台 → Gateway MCP → 需求 Agent → 本体 Agent → 编码与部署。

正式立项前用 1–2 周验证身份/权限、项目 API、Agent 工具链和页面迁移工作量，再收敛资源与排期。采用 WeKnora 底座后，生产升级仍需定制镜像、回归和灰度。
