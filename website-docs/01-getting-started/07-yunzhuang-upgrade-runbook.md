# 云妆 WeKnora 版本升级操作手册

本文记录 `WeKnora-dsh` 的 `yunzhuang-ai` 分支从 v0.8.2 升级到 v0.8.3 的经验，供以后升级到 v0.8.4 等版本时复用。**每次都以目标版本标签和该版本的升级须知为准**；下文的镜像号、扩展号、迁移号及数据量仅是 v0.8.3 的实测记录。

## 1. 升级前填写记录

在执行命令前，把本次的值写进工单或私有记录；不要把密钥、数据库密码和生产 `.env` 提交到仓库。

| 项目 | 本次填写内容 | v0.8.3 案例 |
| --- | --- | --- |
| 源版本、目标上游标签 | `v<old>`、`v<new>` | v0.8.2 → v0.8.3 |
| 自定义分支、升级前提交 | 分支名、完整 SHA | `yunzhuang-ai` |
| 旧部署目录、新部署目录 | 绝对路径 | `/opt/weknora-v0.8.2`、`/opt/weknora-v0.8.3` |
| Compose 项目名 | 从旧部署的容器、卷和配置确认 | `weknora-v082` |
| PostgreSQL 主版本、ParadeDB 镜像与扩展版本 | 升级前和目标版本 | 见末尾实测记录 |
| 当前迁移版本、目标迁移范围 | 从数据库与目标版本升级须知确认 | 110 → 118 |
| 数据卷、绑定目录、其他写入方 | 从实际 Compose 配置列出 | 含 Langfuse、MinIO 等 |
| 入口与验证账号 | 端口、域名、可用的测试账号 | 官方 18080、云妆 18082、应用 18081 |
| 维护窗口、备份位置和恢复负责人 | 私有记录 | 备份必须位于数据卷之外 |

先阅读目标版本的 `website-docs/07-releases/v<new>.md` 中的**升级须知**、其引用的数据库升级文档和 `CHANGELOG.md`。逐项列出数据库迁移、镜像及扩展、配置语义、前端、索引、数据回填与重解析要求。若目标版本变更 PostgreSQL **主版本**，须另拟跨主版本迁移方案，不能直接沿用本手册中的数据卷切换步骤。

## 2. 合并代码并保留云妆改动

1. 确认工作区状态、远端及目标标签。保护未跟踪文件，尤其是 `frontend/output/`，不要使用清理命令误删。确认上游标签已完整获取，避免部分克隆缺少 Git 对象。
2. 从自定义分支合并**固定的上游发布标签**，不要以会继续变化的 `main` 代替。逐文件解决冲突，对照升级前版本检查云妆 Logo、登录与注册页、品牌色、导航与文案、收藏入口和权限规则；同时接入目标版新增功能。留意无冲突但行为已被上游改写的文件。
3. 完成前端依赖安装、构建、类型检查及受影响功能的测试。按仓库现行样式守卫规范处理新增样式。查看完整差异和 `git diff --check` 后提交、推送 `yunzhuang-ai`，记录合并提交 SHA。
4. 若 HTTPS 推送无凭据，可使用已授权的 SSH 远端。遇到 `fatal: unable to read ...` 等对象缺失错误，先完整获取上游标签及其历史对象，再重新推送；不要把不完整仓库当作部署来源。

## 3. 制作部署包与差异清单

旧生产目录可能没有 `.git`，应以已验证的合并提交制作新目录或包，并保留旧目录。先从旧部署读取实际生效的 Compose 配置，再比较新旧配置：

```bash
docker compose -p <existing-project> -f <compose-file> config --services
docker compose -p <existing-project> -f <compose-file> config --volumes
docker compose -p <existing-project> -f <compose-file> ps -a
```

命令中的占位符必须替换为本次真实值；若部署使用多个 `-f` 文件，每条命令都按相同顺序传入。`docker compose config` 会展开环境变量，输出可能含密钥，**不要把完整输出贴到公开日志或工单**。逐项确认以下配置：

- 固定原 Compose 项目名。新目录默认会改变项目名并创建另一组卷；可在新 `.env` 中设置 `COMPOSE_PROJECT_NAME=<existing-project>`，执行时也显式传 `-p <existing-project>`。核对卷的实际名称和挂载目标，再启动服务。
- 复制并逐项比对原有 `.env`、`config/config.yaml` 及各 Compose 覆盖文件。保持 `SYSTEM_AES_KEY`、`JWT_SECRET`、签名密钥、数据库密码和存储配置原值；不要用示例文件覆盖。把目标镜像标签固定为发布版本，避免 `latest` 漂移。
- 保留双前端：官方入口使用目标版正式 UI，云妆入口使用合并代码构建的 UI；确认两者代理到同一目标版后端、端口与域名不变。云妆静态文件须以 Docker 构建模式生成。核对现有 Docker socket 挂载、MinIO 镜像、Langfuse、解析服务和其余自定义覆盖配置。
- 用 `docker compose ... config` 检查最终服务、网络、卷、端口和镜像，并核对新旧配置差异。不要通过修改目录名顺带更换卷，也不要执行 `down -v`。

## 4. 备份与独立演练

1. 清点**所有**数据库、角色、文件存储、配置、命名卷与匿名卷，以及同机依赖服务的数据。按实际部署纳入 PostgreSQL、文件卷、Redis、Neo4j、Langfuse ClickHouse、MinIO 等；不要仅备份 WeKnora 主库。
2. 在空间足够且位于数据卷之外的位置做预备份。将 `pg_dumpall` 的全部数据库与角色备份、停止后的数据卷归档、配置归档分别保存，限制文件权限（如 `umask 077`）。生成 SHA-256 校验文件；用 `gzip -t`、`sha256sum -c` 验证归档。加密或限制访问，备份含敏感配置。
3. 在**独立数据库卷和隔离网络**恢复备份，实际启动目标数据库镜像、升级扩展、启动目标应用执行迁移，再核对表、索引、数据量与关键检索。PostgreSQL 首次初始化期间可能短暂接受连接；恢复前还须等待日志出现 `PostgreSQL init process complete`，不能仅凭 `pg_isready`。
4. 记录演练时长、空间用量、目标迁移版本、`dirty` 状态、扩展版本和异常处理。恢复或演练失败时先修复方案，不能直接进入生产切换。

## 5. 生产切换顺序

1. 在维护窗口停止 WeKnora 应用、文档解析与所有数据库写入方；同机 Langfuse 的 web/worker 也要停。确认无活动写入后制作**最终** `pg_dumpall`，再停止数据库及相关数据服务，对所有相关卷和配置制作最终归档、校验并记录备份路径。保留旧部署包与备份。
2. 仅在独立演练已证明兼容时切换目标 ParadeDB/PostgreSQL 镜像，保持既有 PostgreSQL 主版本和卷。先启动数据库，确认健康。在**每个实际安装了 `pg_search` 或 `vector` 的数据库**分别升级已安装扩展，然后查询 `pg_extension` 验证结果；包括可能安装了扩展的模板库。未安装扩展的库直接跳过，不要为了升级而安装。扩展升级 SQL 应按目标版本文档确定，绝不在新镜像执行旧版扩展的固定版本升级命令。
3. 确认镜像与扩展版本匹配、索引有效、数据库稳定后，启动目标版后端，观察自动迁移日志与迁移表，要求达到目标版规定的版本且 `dirty=false`。若迁移中断，不要盲目重试或手工改迁移版本；先核对数据库状态和报错。
4. 启动官方与云妆两个前端、解析服务、Langfuse 及其他依赖。检查两个入口、后端健康、容器状态与日志。避免在旧后端仍写入时启动新后端。

## 6. 验收与回滚判据

升级前后比对用户、知识库、文档、消息、分块、向量等核心数据量，并抽查原有数据。使用测试账号走完登录、注册策略、文档上传与解析、知识库检索和引用、对话、Agent 工具及 Langfuse 链路。检查官方和云妆登录页、云妆品牌与菜单、收藏入口，并测试目标版本的新功能。无测试账号时只能验收未登录页面和 HTTP/容器状态，不能声称上传与问答已通过。

若目标版变更注册或 Agent 配置语义，按其升级须知核对实际运行配置和迁移结果。重解析旧文档、重建向量或启用图片向量应按业务需求和目标版说明决定，不要在升级中默认批量执行。发现功能或数据异常，停止新服务并评估恢复；保留现场日志和备份校验结果。

数据库镜像、扩展或应用迁移一旦改变数据，**仅回退镜像标签不足以安全回滚**。从升级前最终逻辑备份或物理快照恢复到**独立数据卷**，验证旧镜像、旧配置与旧应用在该副本上可用，再按回切方案恢复入口。不要在已升级的唯一生产卷上直接尝试旧镜像。

## v0.8.3 实测记录（仅供对照）

- 上游标签 `v0.8.3` 合入 `yunzhuang-ai`，合并提交 `1e391c7c981d9d3b620b94f162cf03a60c83115d`；前端构建、类型检查和 36 项相关测试通过。
- Compose 项目名保持 `weknora-v082`；新目录为 `/opt/weknora-v0.8.3`，旧目录保留。官方前端 `18080`、云妆前端 `18082`、应用 `127.0.0.1:18081`。
- ParadeDB 镜像 `v0.22.6-pg17 → v0.25.11-pg17`；`pg_search 0.22.6 → 0.25.11`，`vector 0.8.1 → 0.8.4`。生产中 `WeKnora`、`paradedb`、`template1` 装有两种扩展；`postgres`、`langfuse` 未安装，升级脚本需跳过后两者。
- PostgreSQL 迁移 `110 → 118`，`dirty=false`；画廊回填 53 行。升级前后 7 用户、119 知识库、534 文档、230 消息、13,320 分块、13,225 向量一致，索引有效。
- 生产最终备份位于服务器 `/opt/weknora-upgrade-20261015/`：`pgdumpall-final.sql.gz`、`volumes-final.tar.gz`、`config-final.tar.gz`、`SHA256SUMS-final`。这些文件含敏感数据，不得提交到仓库。
- 两个前端、后端与 Langfuse HTTP 检查通过；浏览器确认云妆登录/创建账户页及官方登录页。未提供真实账号凭据，**登录后的上传、检索与问答完整流程尚未实测**。
- v0.8.3 特有配置：需要受邀用户注册时，将 `auth.registration_mode=invite_only` 改为 `invite_register`；检查旧 Agent 的工具列表。图片向量保持默认关闭，旧文档未批量重解析。详情见 [v0.8.3 升级须知](../07-releases/v0.8.3.md#upgrade-notes)与 [ParadeDB 存量库升级](06-paradedb-upgrade.md)。
